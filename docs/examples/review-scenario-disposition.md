# Scenario evidence and disposition

These synthetic review exercises illustrate existing contracts; they contain no private product fixtures. They are not a claim that a unit test measures a reviewer's ability to discover defects. Priority and blocking depend on the evidenced consequence, independently of the observation's source.

| Scenario | Contract and actual sequence | What a green test does not establish | Evidence and disposition |
|---|---|---|---|
| State check precedes password | Credential must be demonstrated before state-sensitive rejection/audit; a nested lookup rejects disabled accounts before hashing | A test explicitly expecting zero password calls preserves the disputed behavior | Trace the nested call and audit classification; candidate with concrete disclosure/audit consequence. Timing difference is a risk until measured, not a fabricated measurement |
| Missing status catalog inserts a login success | Missing catalog permits the request but is an operational warning; state validation writes a success row before any session exists | A test asserting that row does not prove the audit classification is correct | Follow producer and audit consumers; report a confirmed classification defect when no login occurred, independently of whether availability is preserved |
| Reactivation from another allowed state | Only DISABLED triggers revocation; handler invalidates sessions for every non-ACTIVE state before SQL commit | Testing DISABLED-to-ACTIVE does not cover other allowed states or SQL failure | Trace transition and cross-store effects; candidate for unintended session invalidation, with bounded conditions |
| New actor index never prunes | Each session adds a member; logout, deletion and natural expiry leave the index; no TTL or pruning exists | Creation/rotation tests do not establish release | Static monotonic accumulation is evidence. Report the bounded resource defect; volume/latency remain unknown and do not justify claiming an outage |
| New reader rejects old records | An older producer omits an identity field; the new reader assumes a conflicting default during the valid compatibility window | New-format tests say nothing about previous persisted data | Inspect both formats and actual window. A confirmed supported compatibility break is a finding; an unspecified rollout guarantee is a public behavior limitation, not silently discarded |
| Integrity parameter defaults to zero | Existing callers pass a snapshot; a hypothetical future caller might omit it | Current happy-path tests cannot establish that the API makes misuse impossible | Optional contract is a design recommendation unless a reachable existing caller produces a concrete failure. Do not label hypothetical future integration a current blocker |
| One read per token becomes three | A batch of N performs N token reads plus two identity reads per token | Success tests do not measure throughput or latency | Count the actual operation path and duplication. Keep consequence credible; report a limited inefficiency if material, without invented response times or mandatory benchmark |
| External review suggests deleting link checks | New hashes can be compared inside the store; older records still require their established validation | Agreement with the external author does not prove the literal fix preserves compatibility | Verify the trust boundary and mixed-format chain. Preserve necessary old checks or demonstrate a safe alternative; reject the unsafe simplification with evidence |

For priority boundaries and comparable cases, see [priority calibration exercises](priority-calibration.md); confirmation, origin and blocking remain separate.

Consolidation uses existing findings and coverage.limitations: confirmed limited defects stay visible even when nonblocking; relevant unresolved behavior gets a public-safe summary; rejected or speculative proposals remain private. Covered means the named scenarios were inspected, not that all possible behaviors were proved.
